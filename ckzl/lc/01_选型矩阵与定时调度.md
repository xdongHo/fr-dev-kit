## 13. Java API vs Python XML 能力矩阵

> **核心原则（2026-08-07 实测更新）**：模板生成**优先使用 FR Java API**（通过 fr-agent `/exec` Nashorn 注入 Designer JVM 执行）。
> Java API 生成的模板格式标准、类型安全、可在 Designer 中正常编辑；Python XML 仅用于读取/格式化/辅助任务（正则改 XML、索引/jcxt/js、探查脚本）。

> **Java API 工作链路**（已验证跑通）：
> ```
> 1. 确保 fr-agent 已注入（localhost:18999 + :19000 存活）
> 2. 通过 /exec (Nashorn) 执行 Java API 代码创建/修改模板对象
> 3. TemplateWorkBookIO.writeTemplateWorkBook(wb, "相对reportlets路径") 写盘
> 4. 路径是相对 reportlets 的（如 "项目分析报表/填报/detail.cpt"）
> ```
> **关键 API 签名（Nashorn 实测验证）**：
> ```
> FRFont.getInstance(name, style, size)     // name="微软雅黑", style=0(常规)/1(粗体), size=9.0(pt float)
> Style.getInstance()                       // 空实例 → deriveFRFont/deriveHorizontalAlignment/deriveBackground 链式调用
> new DefaultTemplateCellElement(col, row, "文本")
> new WorkBook() → wb.addReport(new WorkSheet())
> TemplateWorkBookIO.writeTemplateWorkBook(wb, "相对路径")  // 写到 reportlets 目录
> ```
> **Python 辅助脚本职责**：读取/探查需求 Excel、jcxt/js知识库、格式化已有模板（通配脚本）、fr_check 校验、浏览器预览验证。

| 能力 | Java API (fr-agent /exec) | Python XML (正则) |
|------|:--:|:--:|
| WorkBook 创建 (.cpt) | ✅ **优先** | ✅ |
| Form 创建 (.frm 决策报表) | ✅ **优先** | ✅ |
| EmbeddedTableData | ✅ | ✅ |
| DSColumn + FunctionGrouper | ✅ | ✅ |
| SummaryGrouper | ✅ | ✅ |
| 纵/横向扩展 | ✅ | ✅ |
| 父子格 (rs/cs) | ✅ | ✅ |
| Style (字体/背景/边框/格式) | ✅ | ✅ |
| Formula 公式 | ✅ | ✅ |
| 冻结窗格 | ❌ | ✅ |
| 参数面板 (ParameterUI) | ⚠️ 部分 | ✅ |
| 条件属性 (ConditionAttr) | ⚠️ 部分 | ✅ |
| 超链接 (ReportletHyperlink) | ✅ | ✅ |
| 图表 (VanChart) | ⚠ 图表**对象树**类名未核验（com.fr.chart.chartattr.* / com.fr.plugin.chart.*） / 图表**属性注入**可用（读写两端已核验） | ✅ |
| FRM 组件内容 (图表块/报表块/参数面板) | ⚠️ 部分 | ✅ |
| 填报提交 | ❌ | ✅ |
| 产物格式 | **标准 XML**（Designer 可编辑） | 手工拼接 XML |
| FR 设计器可读性 | ✅ 好 | ⚠️ 需人工校验 |
| 代码量 | 中 | 少 |
| 类型安全 | ✅ | ❌ |
| 参数面板批量布局 | ❌ | ✅ |
| **.cpt 写盘** | `TemplateWorkBookIO.writeTemplateWorkBook(wb, "reportlets相对路径")` | 任意绝对路径 |
| **.frm 写盘** | `form.export(FileOutputStream)` — 写绝对路径 | 任意绝对路径 |

### 13.1 选择建议

> ⚠️ **铁律**：模板生成优先 Java API；格式化/样式任务优先通配脚本；两者都不行才用 Python 正则手写 XML。

| 场景 | 推荐方案 |
|------|---------|
| **从零创建 .cpt 模板（单元格/样式/数据集）** | **Java API 优先**（fr-agent /exec） |
| **从零创建 .frm 决策报表/驾驶舱** | **Java API 优先**（`new Form()` + `form.export()` 写盘） |
| **修改已有模板的单元格/样式** | **Java API 优先**；格式化用通配脚本 |
| 原型验证 / 批量生成 | Java API |
| 含填报提交的模板 | Java API 生成主体 → Python XML 补填报提交配置 |
| 含图表/FRM 组件内容(图表块等) | Java API 生成骨架 → Python XML 补图表/组件细节 |
| 简单行式报表 | Java API |
| **参数面板样式/布局** | **kfgj/tygs优先**（`run_all.py` / `param_panel_style.py`），不要手写 CSS |
| **单元格格式化** | **`fmt_detail_cells.py` 优先** |
| **导出/查询按钮补全** | **`add_export_btn.py` / `add_query_btn.py` 优先** |
| 需求探查 / jcxt/js / 校验 | Python 脚本 |

> **图表 Java 落地通道（doc-1695/663）**：能力矩阵标 ❌ 会让所有图表需求直接放弃 Java 路线；当前阻塞点只是「kit 无已核验类名/方法名」而非 API 不存在（图表交互属性/样式是模板态数据，存活在 .cpt 的 `<Chart>` 子树里）。核验完成前图表族走「Java 建承载层 + 反射/XML 注入图表子树」。反射通道：`TemplateWorkBookIO.readTemplateWorkBook(String)` 读已含图表的基线模板 → 遍历 `getReport(0).cellIterator()`，用 `TemplateCellElement.getValue()` 定位图表容器（判据是返回值类名含 ChartCollection，不依赖类名核销）→ 反射设置属性 → `TemplateWorkBookIO.writeTemplateWorkBook(WorkBook, String)` 写回（doc-3546 useHtml 开关正是「只改一个属性」的典型场景）。

> **单元格内部分字符变色/加粗 —— 决策顺序（doc-2188）**：① 整格变色够用 → 条件属性（`ConditionAttr`+`CommonCondition`+`Formula`，纯模板能力、导出保留颜色）；② 数据库支持正则替换 → **SQL 侧直接产出带标签的列**（`REGEXP_REPLACE(col,'([0-9]+)','<span style="color:red">\1</span>')`，MySQL8/PG/Oracle），模板只开 HTML 显示，零部署；③ SQL Server 等无正则替换、或规则复杂 → 才写自定义函数（编译+两处部署+注册+重启）；④ 有 Excel/PDF 导出诉求 → 上述 ②③ 均不可用，改 SQL 拆列 + 分格设样式。官方文档一上来就给「写自定义函数」这条最重的路，多数场景（数字变色、关键词高亮）在 SQL 里一行正则就解决了。

> **混合模式**：Java API 创建主体（单元格/样式/数据集）→ Python XML 补充（冻结窗格/填报提交/参数面板 ParameterUI）→ 通配脚本格式化（CSS/布局/按钮）→ Python 校验（fr_check + 浏览器预览）。

## 14. 定时调度（schedule）：生成边界与约束

> 定时调度任务配置本身在决策系统、不进 .cpt XML；但它是 headless 产出的 .cpt 最主要的消费方，且有一批规则**纯静态可校验**，违反后运行期静默失败。本节固化「模板生成 → 平台配置」的边界与可无头落地的约束。

### 14.1 能力边界：模板侧 vs 平台侧

- 模板交付侧的「可被某角色调度」需配套「模板认证 > 角色权限认证」元数据（使模板在调度对象选择器中对目标角色可见）；该元数据属 .cpt 内可配置项、可随模板一并产出。
- 「管理/授权某次管调度任务」属决策系统权限（全局开关：分级授权 + 定时调度管理，10.0.18+ 起管理/授权解耦），不在模板生成链路。
- 来源:帆软官方帮助 doc-4158

### 14.2 执行条件=公式判断

- 调度公式直接引用 .cpt **物理单元格坐标**（如 `D5<20000`），不是参数也不是数据集字段；true→执行推送，false→跳过/延迟。
- 公式语言是受限子集（doc-3315「定时调度支持的公式」），可引用报表单元格与 `${today()}` 等系统函数，不是任意 JS。
- 「公式→指标坐标」配置中间态骨架：`practice/topic_688/dispatch_formula_spec.json`。
- 任务重启三字段：「如果任务中断按以下频率重新启动」勾选 / 两次重启间隔（分钟） / 最多尝试重启次数。
- ⚠️ **最致命的静默故障**：指标单元格坐标一旦在模板改版中漂移，公式永远 false、预警永不触发，而任务建立/运行全程正常，无人察觉。生成期应校验公式引用的坐标存在且为数值（fr_check 可加「公式判断引用单元格」静态规则）。
- 来源:帆软官方帮助 doc-688

### 14.3 挂载平台

- 前置条件：仅「调度对象 > 对象类型 = 报表模板」时可勾选挂载平台。
- **「挂载名称禁止公式、文件名称允许公式」对照**（与 doc-3315 文件名称 `${}` 配对）：挂载名称写成 `${...}` 不会报错，只会当字面量目录名（静默坑）；文件名称可写 `${today()}` 等系统函数。
- 结果报表顶部会显示该次生成时间与使用的参数值，故调度对象 .cpt 应备好参数，否则顶部参数值恒空、难追溯。
- 「目录名 + 部门/角色/用户 查看权限」是平台侧 spec 过渡态（挂载就绪校验见 `practice/topic_2209/check_mount_ready.py`）。
- 来源:帆软官方帮助 doc-2209

### 14.4 送达通道 × 约束对照表

定时簇通道已集齐（邮件/平台通知/短信/客户端/挂载/FTP），各通道公式语法互不通用（`${...}` vs `=$xxx`）、约束各异且极易混写后全部静默失效，用一张表收口：

| 通道 | 独有约束 | 共性前置（全部适用） |
|------|---------|---------------------|
| 邮件（doc-683/684） | 附件存档是固定层级目录树（schedule/任务名/日期/时间/…）；发件人在「系统管理>邮箱」全局唯一配置；`.cpr/.frr` 结果报表文件**不会**作为邮件附件发送 | ① 默认用户组必设（否则消息发不出去、任务照常成功）② 主题必填且用 `${...}` 公式（如 ${today()}）③ 结果链接开关 |
| 平台通知（doc-4432） | 站内信；默认用户组=收件人；主题/内容支持 ${today()} 公式；链接开关（结果链接在平台内打开/无） | 同上 |
| 短信（doc-2210） | 独有公式 `=$taskname`/`=$time`（`=` 前缀，与模板 `${...}` 系统函数区分，混写静默失效）；`${fine_username}` 仅「调度对象=报表模板 + 勾选按默认用户组单独生成结果」时生效；短信参数默认值入库有字段长度上限，过长报「任务更新失败」 | 同上（组内用户须绑手机号） |
| 客户端/APP（doc-1387） | 仅链接消息（图文/文件消息静默转为链接）；自定义链接 IP 必须可达（直接粘 localhost 链接 = 任务成功 + 消息收到 + 手机点开空白，全链路零报错）；需推送服务器/代理；主题必填 | 同上 |
| 挂载（doc-2209） | 挂载名称禁公式（见 §14.3） | — |
| FTP 上传（doc-682） | 无收件人概念（默认用户组/主题公式/结果链接三列 **N/A**）；校验重点在「连接+路径」而非用户组/公式 | — |

> 来源:帆软官方帮助 doc-1387/4432/2210/682

### 14.5 FTP / SFTP 上传附件

- **SFTP 优先铁律**：凡无头生成调度 spec 涉及「上传附件到远程服务器」，默认协议写 SFTP（V10.0.18+ 官方推荐；SFTP 选项自 JAR 2020-08-03 起提供，早于此版本只有 FTP），FTP 明文不安全、仅作降级 WARN；SFTP 通常端口 22、可用密钥认证、无传输模式字段。
- **FTP 与 SFTP 必须分列，规则不能互用**（已实测：用 FTP 规则校验官方正确 SFTP 配置会误报并诱导改错路径）：

| 维度 | FTP（doc-682） | SFTP（doc-3573） |
|------|---------------|-----------------|
| 端口 | 默认 21 | 通常 22 |
| 传输模式 | 主动 / 被动 | 无 |
| 保存路径 | **相对路径优先**（官方明注「/文件夹」超时不落盘，删掉开头的 `/` 重传即可；该 `/` 前缀坑**仅 FTP 适用**） | 语义由 SFTP 服务器所在 OS 决定：Windows=相对 SFTP 根目录、根目录本身写 `/`；Linux=必须绝对路径 |
| 认证 | 密码 | 密码 或 OpenSSH 格式密钥（`.ppk` 连不上；用密钥须关闭平台「文件上传校验」开关） |
| 前置 | — | 对象类型必须=报表模板；附件存档须勾选格式（不勾则任务成功但 SFTP 上无产物） |

- **认证选型**：默认 auth_mode=key（OpenSSH 格式），避免明文口令写进 spec 文件并进版本库；仅密钥不可用时降级为 password 并 WARN。
- 来源:帆软官方帮助 doc-682/3573

### 14.6 模板交付给定时调度时的前置约束

定时任务无人值守执行，模板必须满足：

1. 所有模板参数有默认值（调度侧不弹参数面板）；
2. 不依赖前端交互控件取值（`_g()`/`window.contentPane` 在调度渲染时不可用）；
3. 数据集执行时间受 `ScheduleSettingConfig.taskTimeout` 限制，慢 SQL 会直接判任务失败；
4. 若按用户分发结果，模板过滤条件需用 `$fine_username`。

> 以上任一不满足都表现为「预览正常、定时任务报错」，属高频返工点。

> 来源:帆软官方帮助 doc-663

### 14.7 定时任务配置的 Java 骨架与边界

以 `com.fr.schedule.base.bean.ScheduleTask / TaskCondition / TaskParameter` 三件套为骨架，首篇收「执行条件」：

- `TaskCondition.NORMAL=0 / FORMULA=1 / CLASS=2`（对应 `DefaultTaskConditionEvaluator.TYPE=0` / `FormulaTaskConditionEvaluator.TYPE=1` / `ClassTaskConditionEvaluator.TYPE=2`）；
- 自定义类扩展点 `com.fr.schedule.base.provider.ExecuteCondition` 及其 `impl.AbstractExecuteCondition` / `impl.AbstractParameterExecuteCondition`。

**开篇必须写清边界：定时任务配置持久化在 FineDB（`TaskConditionEntity` 只有 `{type, description}`），完全不落 .cpt XML，fr_check.py 管不到** —— 使用者按 kit 既有心智（一切皆 XML）去找「执行条件写在哪个节点」会一无所获，「找不到」比「找错」更浪费时间。

> 来源:帆软官方帮助 doc-1485

### 14.8 定时任务 Java 装配链（ScheduleTask 三层骨架）

骨架三层（均已字节码实读）：

- `com.fr.schedule.base.bean.ScheduleTask`（`setTaskName / setTemplatePath / setTriggerGroup / setUserGroup / setScheduleOutput`）；
- `com.fr.schedule.base.bean.ScheduleOutput`（`setBaseName / setFormats / setCreateAttachUsername / setOutputActionList`）；
- `com.fr.schedule.base.bean.output.BaseOutputAction` 的各子类。

落库入口 `com.fr.schedule.feature.service.v10.ScheduleTaskService.getInstance().addTask(String operatorUserName, ScheduleTask)`（⚠ **无单参重载**，而 updateTask 单参双参都有）。

触发器：`TriggerGroup#setTriggers(List)` + `CronExpressionTrigger#setCronExpression`；起止走 `BaseTrigger` 常量（START_IMMEDIATE=1/START_ON_TIME=2、END_ONCE=1/END_UNLIMITED=2/END_ON_TIME=3/END_ON_REPEAT=4）。

接收人：`com.fr.schedule.base.user.PlatformUserGroup#setPlatformUser(List)`（UserGroup 为抽象类）。

`com.fr.schedule.base.type.RunType` 全表：CREATE_SNAP=0 / SEND_EMAIL=1 / SEND_FTP=2 / PUSH_MESSAGE=3 / FILE_PRINT=4 / SEND_SMS=5 / MOUNT_DIR=6 / CUSTOM_CLASS=7 / REPORTING_ACTION=8 / CLIENT_NOTIFICATION=9 / SEND_SFTP=10 / SEND_FILE=11。

> 换一个 action 子类就复用——邮件/FTP/短信/打印/挂载目录等 11 种输出方式共用同一装配链，一章的边际收益覆盖整个 RunType 家族。

> 来源:帆软官方帮助 doc-3531

### 14.9 per-user 分发能力边界

- 可无头构建：.cpt 侧「服务器数据集 + 列过滤 `$fine_username` + 系统参数」（practice/doc-697）；
- **不可无头构建：「根据默认用户组单独生成结果」这一开关本身是数据决策系统配置项，kit 无对应 Java API**，不能端到端无头生成定时任务。

> 调度任务定义（基本设置/调度周期/本地文件/文件处理）全在决策系统 GUI，不在 Java 构建范畴；不划清会误导生成器设计。

> 来源:帆软官方帮助 doc-697

## 15. 模板外部依赖清单

「模板外部依赖清单」从建议落成正式产物，统一 schema，至少三个分册；部署脚本消费该清单，输出「目标工程还需建哪些连接、给哪个账号授哪些权」：

1. **工程全局参数**（doc-159，project_globals.json）：跨工程搬运模板时全局参数不会跟着 .cpt 走，须在远程工作目录重新设定。
2. **扩展图表插件版本**（doc-2474）：凡模板含扩展图表，记录其创建所用插件版本，部署脚本输出「目标工程须装扩展图表插件且版本 >= 此版本」——插件未安装/被禁用/版本低于模板创建版本/本地与远程版本不一致 → 「图表初始化失败，无法打开模板」。扩展图表另有四类静默不支持：不支持导出 / 不支持移动端 / 不支持任何图表接口 / 只支持 Chrome(>=86) 预览；且依赖 `%FR_HOME%/lib` 下 jxbrowser 开头的 2 个 JAR（缺失 → 初始化失败）。
3. **数据连接名 + 使用权限 + 全局开关 + JAR 日期**（doc-4152，conn_permission_manifest.json）：数据连接控制默认关闭，生产一开启所有未授权模板同时失效；2022-08-03（10.0.19）是版本闸门（旧 JAR 上"能跑通"不能证明权限配对了；升 JAR 前先补授权）；超管绕过连接鉴权，自动化校验必须对「当前是超管」发警告。
   - 数据连接分册补两个字段（doc-2406）：`connectionType`（固定 `"jdbc"`，决定平台侧走哪个 `ConnectionTypeProcessor`，注册表实读只有 jdbc/jndi/plugin 三个）与 `driverJars`（需落到 `WEB-INF/lib` 的驱动 jar 清单 + 是否需重启）。驱动 jar 是 **classpath 级依赖**，既不在 .cpt 里也不在 FineDB 里，漏一个就是「连接配置全对但 loadClass 失败」（如 Caché 要求解压后 4 个 jar 全部落 lib 并重启）。

4. **插件依赖 plugin_manifest.json**（doc-1481）：schema `{name, minPluginVersion, minJarDate, reason, source}`。首批两条均由 `rowEngineEnabled=true` 触发：「定时器导出任务支持行式引擎」（V1.4.4/V1.3.3，JAR≥2016-01-01，doc-1481）、「Excel 流式导出支持行式引擎」（doc-1407）。**关键性质：插件装没装在 .cpt 里零痕迹**（官方明写「安装后无需做额外设置」），静态检查原理上不可判，只能靠清单传递。

5. **运行环境声明 runtime_env.json**（doc-3814）：schema 建议 `{jdk_version:"1.8", jdk_update_min:102, arch_bits:64, java_awt_headless:true, file_encoding:"UTF-8", native_libs:["libXrender.so.1","libXtst.so.6","libj2v8_linux_x86_64.so"], tomcat_min_version:"8.5.57", connector_attrs:{URIEncoding:"UTF-8", maxPostSize:"-1", maxHttpHeaderSize:16384, relaxedQueryChars:"[]{}\^\"<>"}, jvm_opts:["-Dfile.encoding=UTF-8","-Djava.awt.headless=true"]}`。与 `delivery_channels.json`（doc-1481/4068）、`plugin_manifest.json`（doc-1481）配对：**模板要去哪儿 / 目标机器长什么样 / 要装什么插件**三份产物合起来才是完整交付。

6. **决策平台用户/角色权限**（doc-773）：该权限**存于 FineDB，.cpt XML 里零痕迹，静态检查原理上不可判**；交付自检只能在运行期用 `doesUserHaveAuthority(userId, entityId, AuthorityType)` 对 (用户, 模板节点) 逐对断言。

> 这已是同一模式（.cpt 里只有引用、声明在工程侧、缺失时静默或以误导性形态失败）的第三次验证，应作为统一产物而非逐篇打补丁。
> 来源:帆软官方帮助 doc-4152/2474/1481/3814/2406/773

**插件依赖模板通用机制（doc-3321）**：凡模板 XML 中出现插件私有节点/类名（已知两例：doc-786 的 Excel03 ShortCut name、doc-3321 的 Sheet 链接 class），生成器必须同时产出部署清单（插件名+版本+JAR 版本下限+设计器/服务器安装范围），且私有类名一律标注【待核验】、以真实设计器保存后 diff 取值回填，严禁猜测硬编码——写错时 FR 一律静默不生效。同时统一登记「Excel 导出增强类插件均不支持移动端」（doc-1121/786/3321 三篇一致）。
