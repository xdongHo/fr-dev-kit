## 10. 产物分类：模板类 / 平台实体类 / 配置项类（doc-2406）

> 来源: 帆软官方帮助 doc-2406

FR 无头产物从两类扩为**三类**：

| 类别 | 形态 | 校验方式 |
|------|------|----------|
| 模板类 | .cpt XML | 可 diff / fr_check |
| 平台实体类 | FineDB 表 | Service 写完 find 回来验 |
| **配置项类** | `com.fr.config.DefaultConfiguration` 子类 + `com.fr.config.holder.Conf` 字段（样板 `com.fr.decision.config.mobile.MobileConfig`，一个类装移动端 26+ 项设置） | **两头不靠**：无 XML 可比对，也不走 Service#add/find |
| **图片类（doc-1086）** | 导出产物 png/jpg 等（入口 `com.fr.io.exporter.ImageExporter`，fine-report-engine） | 文件存在性 + 尺寸/像素采样 |

> ⚠️ **能力边界：引擎侧无法生成动图 GIF（doc-1086，架构决定）**——`com.fr.stable.encoder.GIFEncoder` 4 个构造器全是单张 Image/ImageProducer，无 frame/delay/loop 入参，全 jar 唯一引用点 `com.fr.stable.ImageUtils`。凡需求是「导出动图/录报表动效」，**直接判定不可实现**，终止无效搜索，不要投入时间找 API。

硬性规则：**写这类配置必须包事务**——

```java
com.fr.transaction.Configurations.update(new Worker(){
    public void run() { /* XxxConfig.getInstance().setXxx(...) */ }
    public Class<?>[] targets() { return new Class[]{ XxxConfig.class }; }
});
```

裸调 setter 只改进程内存。漏掉事务的症状是「当次调用成功、界面也变了、重启还原」——与「设置没生效」表现完全不同却极易混为一谈，且无头环境下没人会去重启验证。读可直接 `XxxConfig.getInstance().getXxx()`。

> ⚠️ **铁律例外（doc-1698）**：**部分 Config 的 `putXxx/setXxx` 自身已经包了事务**——调用前先 `switch_probe`/`invoke_owner_probe` 看方法体里有没有 `Configurations.update`。实例 `com.fr.base.MapLayerConf#putMapLayer(String, MapTileLayer)` 字节码 = `new MapLayerConf$1(...)` + `Configurations.update(Worker)`，外面再包一层属**多余嵌套**。铁律不是全称命题：盲目套用虽不致错，但会掩盖「到底哪一层负责事务」的判断，批量写入时产生嵌套事务疑虑。
> 来源: 帆软官方帮助 doc-1698

> 📌 **平台类配置的 Service 层入口常带 `HttpServletRequest`（doc-1163）**：用于写 `Dec-*` 操作日志——无头场景没有真实 Servlet 请求，应改走 `XxxConfig.getInstance().setXxx() + Configurations.update(WorkerAdaptor)`，**显式代价是丢失平台操作日志**。另：decision 层 `setXxx(Bean)` 的覆盖语义**逐个不同**——doc-3050 的 `MobileEntryConfigService` 每字段 `ifnull` 部分更新 vs doc-3474 的 `MobileOtherSettingsService` 标量无条件全量覆盖，**禁止跨 Service 推断**（默认全量覆盖会写出多余读取步骤，默认部分更新会在别处覆盖存量配置，两条互斥经验必须同时在场并「逐 Service dump」）。
> 来源: 帆软官方帮助 doc-1163

## 11. 运行环境体检（doc-2406 / doc-4130 / doc-3860）

> 来源: 帆软官方帮助 doc-2406 / doc-4130 / doc-3860

### 11.1 配置项引用完整性（doc-2406）

把体检规则从「FineDB 是否回落内置库」推广为一条通式：**凡配置项存的是「类全限定名 / 插件 id」这类引用值，都必须能在对应注册表里 find 回来，否则告警**。首批可落地两条：

- `MobileConfig#getActiveTheme()` 非空且非 `"default"` 时，须存在于 `ExtraMobileClassManager.getInstance().getArray("MobileThemeProvider")`；
- `selectedEntryStyleId` 等同族字段同理。

> ⚠️ 默认值判定要 **`""` 与 `"default"` 双认**（`<init>` 里是空串，读取分支判的是 `isBlank || equals("default")`）。与「外接库静默回落 HSQL」同一种失败形态：配置还在、界面正常、日志只有 info 级，用户侧表现为「我明明配了红色主题，APP 上还是蓝的」。

### 11.2 WebSocket 体检项：三元比对（doc-4130）

判据是**三元比对**不是单一布尔：

1. `com.fr.web.socketio.WebSocketEnv.isStartup() == false` → 平台已进/将进部署向导页，消息推送、填报校验提示、定时刷新等一并失效；
2. isStartup 为 true 但 `WebSocketEnv.getRunningPort()` **不在** `WebSocketConfig.getInstance().getPort()` 列表内 → 配置改过但没重启（界面上完全看不出来，`getPort()` 读回的就是新值，只有 `getRunningPort()` 会露馅）；
3. `getProtocol()==SSL` 而 `getKeyStore()` 为空 → configSSL 会失败。

> ① 与平台自身判据完全一致（`WebSocketChecker#doCheck()` 字节码只有 `WebSocketEnv.isStartup()` 一句）。WebSocket 挂掉的用户侧表现是「填报/刷新/推送莫名不好使」，与模板本身毫无关系。

### 11.3 单复数并存配置字段的迁移点（doc-4130）

**新旧字段并存时的自动迁移点可能不在 Config 类里，而在 Activator 的启动路径上**。样板：`WebSocketConfig.requestPorts` 构造器默认 `new Integer[0]`，真正把旧的单数 `requestPort`（38889）迁进去的是 `WebSocketActivator#configRequestPorts()`（`if (ArrayUtils.isEmpty(getRequestPorts())) Configurations.update(...)`），**只有走完整引擎启动才会执行**。

> 规则：凡遇到 `xxx`/`xxxs` 单复数并存的配置字段，读复数为空时必须**回退读单数**，不能直接判定「没配」。这也解释了官方注意事项「两者不能同时存在于 fine_conf_entity，否则会出错」的真实语义：引擎侧是**以复数为准、单数静默失效**，不是报错。

### 11.4 FineDB 配置文件路径 VM 参数只在读时生效（doc-3860）

`-Dfine_db_config_path` **只在读时生效**：`LocalDBPropertiesProvider#get()` 会优先读该路径，但 `save(byte[])` 里完全没有这个 key，无条件写 `<workroot>/config/db.properties`。把 db.properties 外置（容器化/多实例共享配置）后，只要有人在平台里点过一次「保存」，新配置就落到另一个文件，重启后读回的仍是老配置——修改静默丢失，且两个文件都真实存在，排查时极易被误导。

## 12. 无头运行上下文与 Workspace（自检 / 挂载 / 切换）

> 无头链路最靠前也最贵的失败点：上下文没建好时**全链路静默**（日志全成功、磁盘零产物）。本节四条为开工前置，全部字节码实读（FR 10.0.19 / build 2024.03.19）。

### 12.1 无头运行上下文自检（开工前置，doc-1086）

任何无头构建流程开头必须跑的三条断言（固化成脚本/代码模板）：

1. `com.fr.workspace.simple.SimpleWork.checkIn(<WEB-INF 绝对路径>)` 之后立刻断言 `WorkContext.getCurrent().getPath()` 等于入参——未 checkIn 时 `WorkContext.getWorkResource()` 回落 `EmptyWorkResource`，其 write 只往内存 Map put，`TemplateWorkBookIO.writeTemplateWorkBook` 返回 true 却**零产物**；
2. 断言 `com.fr.state.SateVariableManager.get("fineServletURL") != null`，为 null 则先 `remove` 再 `put` 补齐 `fineContextPath`/`fineServletURL`（常量在 `com.fr.stable.web.WebServerConstants`；`put` 对已存在 key 直接 `throw new RuntimeException("Duplicate state key "+key)`，所以**必须 remove+put**，顺序照抄 `MockServletStartUp`）——`$fineServletURL`/`$fineContextPath` 的唯一 put 点是 `DecisionServletInitializer#start()` 与 `MockServletStartUp#start()`，两者都要真实 `ServletContext`，无头链路里**从来没被赋过值**，`DefaultNameSpace#getVariable` 返回 null，模板里用它拼图片/超链接地址的导出产物就是**空串、无任何日志**；
3. 预览 URL 一律用 `com.fr.base.ServerConfig.getInstance().getServletName()` 拼，**禁止硬写 `/decision`**。

> 注：`WEB-INF` 根路径是同一个值的三处用途——`SimpleWork.checkIn` 入参 = `$ENV_HOME` = `SimpleWorkResource` 相对根。
> 来源: 帆软官方帮助 doc-1086

### 12.2 工程根与 Workspace 挂载（doc-1698）

已字节码实读的开合模板：

- **工程根 = `<部署目录>/webapps/webroot/WEB-INF`**（`ServerWorkspace#build` 的 exploded 分支直接用 `sc.getRealPath("/")+"WEB-INF"`）；
- 目录名一律取 `com.fr.stable.project.ProjectConstants` 常量（`WEBAPP_NAME='webroot'`/`WEBINF_NAME='WEB-INF'`/`REPORTLETS_NAME='reportlets'`/`EMBED_DB_DIRECTORY='embed'`/`FINE_DB_NAME='finedb'`/`CONFIG_DIRECTORY='config'`/`LIB_NAME='lib'`/`CLASSES_NAME='classes'`/`PLUGINS_NAME='plugins'`/`DRIVERS_NAME='drivers'`/`LOGS_NAME='logs'`），**禁止硬编码字符串**；
- 挂载 `com.fr.workspace.simple.SimpleWork.checkIn(webInf)`、收尾 `checkOut()`——**checkOut 之后不得再调任何模板读写**；
- 工程名（URL 第三段）= `com.fr.stable.ProductConstants.getWebAppName()`，可用 `setWebAppName(String)` 显式对齐。

> 完整证据见 `practice/topic_2804_java/README.md`。
> 来源: 帆软官方帮助 doc-1698

### 12.3 工作目录切换三铁律（doc-2365）

1. `SimpleWork.checkIn(path)` 的 path 必须指到工程 **WEB-INF** 目录（`ProjectConstants.WEBINF_NAME`），模板相对路径再拼 `reportlets`；
2. 同一 JVM 内切换工程**直接再 checkIn 新路径，禁止先 checkOut**（`SimpleWorkspace` 未 override equals，新实例恒不等于 current，不会被 `switchTo` 的相等短路挡掉）；
3. **`SimpleWork.checkOut()` 不复位 `WorkContext.current`**——它调的 `WorkContext.switchTo(null)` 首句 `aload_0; ifnull → return` 是空操作，checkOut 后 `getCurrent().getPath()` 仍返回旧目录、`isLocal()` 仍 true，只有 `getWorkResource()` 退化成 `EmptyWorkResource`。故「当前在哪个工程 / 是否已退出」的判定一律用 `WorkContext.getWorkResource() instanceof EmptyWorkResource` 或 `new File(path,"reportlets").isDirectory()`，**禁止用 `getCurrent()`**。

> 第 ③ 条是静默坑：`getCurrent()` 是最自然的「我在哪」判据，而它在 checkOut 后永久说谎，配合 `EmptyWorkResource#write` 写内存 Map + `writeTemplateWorkBook` 恒返回 true，会产出「日志全成功、磁盘零产物」的批处理。
> 来源: 帆软官方帮助 doc-2365

### 12.4 无头启动 preflight 五条（软硬标注，doc-1163）

| # | 检查项 | 硬/软 |
|---|--------|-------|
| P1 | `SimpleWork.checkIn(root)` 后断言 `WorkContext.getWorkResource()` 不以 `com.fr.workspace.empty.` 开头 | **硬** |
| P2 | 目录可写性走 `com.fr.decision.fileserver.FineFileServer.getInstance().hasReadWritePermission(ResourceModuleContext.getRealCurrentRepo(), workRoot)` | **硬** |
| P3 | `reportlets` 目录存在 | **硬** |
| P4 | FineDB 可达（`com.fr.decision.deployment.*` 有整套官方自检 API） | **软**（仅平台类产出需要） |
| P5 | tools.jar（`FineAssist.containsToolsJar()`） | **软**（仅 attach/智能运维需要） |

> ⚠️ 把 P4/P5 当硬前提会让**纯模板生成脚本**（纯 .cpt/.frm 产出，既不碰 FineDB 也不碰 attach）在健康环境里拒绝启动。软硬之分与 doc-3855「模板类 vs 平台类」二分同源。
> 来源: 帆软官方帮助 doc-1163

## 13. 无头运行时 classpath 的官方定义与版本自检（doc-1163）

帆软官方「服务器小版本升级」需替换的 **12 个 jar**（fine-accumulator/activator/core/datasource/decision/decision-report/report-engine/schedule/schedule-report/swift-log-adaptor/third/webui，均 -10.0.jar）即 FR 无头开发的**完整运行时 classpath**，与本仓 `C:/frjars` 下 fine-* 逐个一致、无一多余；设计器多出的第 13 个 `fine-report-designer-10.0.jar` 放 `%FR_Home%/lib`（不是 WEB-INF/lib），纯 GUI 侧、无头用不到。

配套版本自检三行（kit 至今没有「我现在跑在哪个 FR 版本上」的可执行判定，而字节码实读结论全部版本相关，跨版本复用笔记前必须先自检）：

- `GeneralUtils.getVersion()`——小版本，读 fine-core 内 `version-core.txt`；
- `readFullVersionNO()`；
- `readBuildNO()`——= 文档口径的「JAR 包时间」，读 fine-report-engine 内 `report_build.txt`。

> 本机实测 10.0.19 / 2024.03.19。

## 14. 无头任务的 PID 标记与幂等（doc-1698）

长跑无头任务用官方现成标记机制：`com.fr.decision.detect.ThreadRedundantDetectByFile` 是 **public 构造器 + 5 个 public 方法**，可直接 `new ThreadRedundantDetectByFile("assist/headless/<job>.pid")` 复用——`addMark()` 写当前 PID、`isRedundant()` 判上次是否未正常结束、`getRedundantPid()` 取旧 PID、`addShutDownHook()` 挂 JVM 退出自动清理。三条使用约束：

1. **不要复用官方路径 `assist/deploy/pid.txt`**（那是部署态 Activator 独占）；
2. 调用顺序必须 `removeMark(); addMark();`——`addMark()` 首句 `pc4 ifne → 33` 是「标记已存在即静默 return」，不照抄顺序会导致标记文件里永远是第一次的旧 PID；
3. 路径相对 WorkResource 根，必须先 `SimpleWork.checkIn(root)`。

> 来源: 帆软官方帮助 doc-1698

## 15. 何时必须走 Java 编译（doc-1698）

「无头 XML 路线无法覆盖」的能力边界共 5 类（源自 doc-744），必须走 Java 编译链路，**不要试图用 XML/Python 无头硬凑**：

1. 程序数据源；
2. 程序报表；
3. 自定义函数；
4. 自定义后台导出；
5. 自定义打印。

## 16. 架构与 OS 判定的正确口径（doc-1698）

写跨平台脚本或判定 ARM 环境时，四条硬事实（零成本可核）：

1. **`uname -m`（内核硬件名）与引擎判定不是一条链**：`com.fr.stable.os.Arch.getArch()` 只读 `System.getProperty("os.arch")`，逐项 `equalsIgnoreCase`——x86={x86,i386,i486,i586,i686} / x86_64={x86_64,amd64,k8} / ARM={ARM,aarch64} / 全不中返回 `UNKNOWN` 且**不抛不记日志**。Linux x86_64 上 `uname -m`=x86_64 而 `os.arch`=amd64，字面量不同、都能命中 `Arch.x86_64`，但拿前者输出比后者字符串会错；
2. **引擎 fork uname 用的是 `uname -a`**（`com.fr.stable.os.Utils.getUname()`），结果只喂给 `getDetailedString()` 展示，不参与任何判定；
3. **OS 判定必须用 `com.fr.stable.os.OperatingSystem`**（enum，有 `isLinux()`）；**旧的 `com.fr.stable.OperatingSystem`（无 `.os` 包段）没有 `isLinux()`**，且是 `isMacOS()` 而新类是 `isMacos()`——IDE 自动补全大概率补错的那个；
4. `AbstractOperatingSystem#setArch(Arch)` 是 public 且 `getOperatingSystem()` 带 static 缓存，**任何一次调用即全局污染**，只读一律走 `Arch.getArch()`。

> `Arch.UNKNOWN` 的两条传染链（native 库落 `_x86_64.so`、在线升级 `$arch="Unknown"` 取不到包）现象都表现为「没反应」，不写清楚排查会跑偏。
> 来源: 帆软官方帮助 doc-1698
