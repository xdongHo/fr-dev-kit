## 15. 层级坐标

```python
# 横向扩展后占比
"=B2/SUM(B2[!0])"      # B2 占所有 B2 总计的比例

# 环比
"=C4/C4[B4:-1]"         # 上一行

# 同比
"=C4/C4[A4:-1,B4:+0]"   # 上一分组同位置

# 序号
"=&A2"                   # 当前行号

# 累计
"=I4[B4:-1]+C4"          # 上一行累计 + 当前值
```

### 15.1 层次坐标语法速查（doc-1914 + doc-4005 + doc-1782）

> 来源: 帆软官方帮助 doc-1914（层次坐标）/ doc-4005（层次坐标术语）/ doc-1782（绝对层次坐标）

kit 现状是 `COUNT(A2[!0])`（§7.6 排序）、`=B2/SUM(B2[!0])`（§15 占比）、`EVAL("B2[;B1:"+$index+"]")`（§7.3 超链）三处各自解释一遍 `[!0]`，没有任何一处定义 `&`/`$`。唯一定义表：

| 语法 | 含义 |
|------|------|
| `Cellx[!0]` | 取全部扩展值（不受父格约束） |
| `Cellx[!0]{条件}` | 条件筛选后汇总 |
| `&Cellx` | 扩展位置（1-based） |
| `$Cellx` | 该位置对应的值 |
| `Cellx[;B1:N]` | 绝对层次坐标 |

**铁律**：层次坐标是**相对父格**的坐标，写公式前必须确认被引用格的扩展方向与左/上父格已显式设置。**三种静默退化**：不扩展 ⇒ `[!0]` 退化为单值/占比恒 100%；`&Cellx` 恒为 1；父格推错 ⇒ 条件筛选语义漂移。Java 侧落点：`CellExpandAttr#setExtendable` / `setLeftParentColumnRow`。

### 15.2 组内排名标准范式（doc-1914）

```
=COUNT(C2[!0]{A2=$A2 && C2>$C2})+1
```

- 与已有「占比 `B2/SUM(B2[!0])`」同属「层次坐标 + `{}` 条件过滤」家族（doc-1914 是分组排名官方文档）。
- **生成器对 `{}` 内条件一律整串写进 `<Attributes>` CDATA、不可拆分 `C2[!0]`**（拆开即静默取错值）。
- 排名列的**左父格须含分组列**（否则静默取错值）；被比较列须**数字型**（文本数字先 `TOINTEGER`）。

### 15.3 左父格层级 vs 移动端折叠树层级（doc-3643）

> 来源: 帆软官方帮助 doc-3643（折叠树）

⚠️ **FR 的「左父格层级」与移动端折叠树插件的「行层级」是两套独立层级**：前者决定数据扩展的父子关系（`<Expand left="B2"/>`），后者决定移动端折叠的树层次（插件属性）——二者**不自动对齐、需人工保证一致**。插件完全不读 Expand 父格信息，只读自己的 level 属性；两者错位时报表能出、能扩展，只是折叠层次与数据层次对不上，肉眼很难发现。生成器应由同一张规格表同时产出这两侧，不要各写各的。

## 16. JS 契约：名字与常量都由生成器供给（doc-2005 + doc-3811 + doc-2369）

> 来源: 帆软官方帮助 doc-2005（Tab 页数/末页索引）/ doc-3811（widgetName 映射）/ doc-2369（树展开层数）

同一范式已三次独立出现（doc-3811 的 widgetName 映射、doc-2369 的树展开层数 t、doc-2005 的 Tab 页数/末页索引）——凡 JS 常量能从模板结构推导，**一律 Java 侧算完再写入 `<Content>`，禁止手填**。

**取值 API 对照**：`Widget#getWidgetName()` / `WLayout#getWidgetCount()` / 父格链层数。

这是无头链路相对 GUI 的**结构性优势点**（而非个案技巧）——GUI 手填必错、无头由结构推导必对；集中成文后可直接作为生成器编码约定，并支撑 fr_check 规则族。

## 17. 平台类配置单例：CacheConfig（doc-2547）

> 来源: 帆软官方帮助 doc-2547（缓存）/ doc-1086 归口；⚠跨模块依赖（平台类产物：落 FineDB fine_conf_entity，非模板 XML）

`com.fr.file.CacheConfig`（fine-core-10.0.jar，`getNameSpace()="CacheConfig"`）：字段 cacheDirectory / maxMemSize（默认 4194304）/ dbConfig / cptConfig（XmlHolder，以 XML 串存）/ alwaysReloadTpl（false）。

两个非直觉点（doc-2547「注意事项」的落点）：

- ① 默认值哨兵是 `new File("")` **而非 null**——`getName()` 空串 = 未设置；故 **fine_conf_entity 里查不到 `CacheConfig.cacheDirectory` 行 ≠ 没配置**（只是还没人调用过 `getCacheDirectory()`）。
- ② `getCacheDirectory()` 是**带写副作用的 getter**（惰性 `Conf.set` + `StableUtils.mkdirs`）且**不在 `Configurations.update` 事务内**——这是目前记录的 Configuration 里唯一「读操作会改库+建目录」的反例，与「平台类配置写必须包 Configurations.update」通则冲突，读写该配置时须知晓。

- 参考 `practice/topic_2547_java/CacheDirectoryOps.java`（读/改 + 回读 + `canWrite()` 双断言）。

## 20. 单元格样式按数据类型规范（Ver0.3 新增）

### 20.1 格式与对齐

| 数据类型 | 格式 (Format) | 对齐 (horizontal_alignment) |
|---------|--------------|---------------------------|
| **日期** (DATE/TIMESTAMP) | `yyyy-MM-dd` | 居中 (0) |
| **数值** (INT/DECIMAL/FLOAT) | `#,##0.00` | 居右 (2) |
| **文本** (VARCHAR/CHAR) | TextFormat | 居左 (1) |
| **序号** | TextFormat | 居中 (0) |

> 注意：FR 中 `horizontal_alignment="0"`=居中, `"1"`=居左, `"2"`=居右。
> 与 §3.5 通配规则一致（文本左对齐、数值右对齐）。

### 20.2 识别方法
通过解析数据集的 DBTableData → Connection → Query 获取 SQL，连接数据库查询 `resultSet.getMetaData()` 获取列类型。
