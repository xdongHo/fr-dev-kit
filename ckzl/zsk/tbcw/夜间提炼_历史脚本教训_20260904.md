## 一、XML 与条件属性族

### 1. 正则重建 `<C>` 标签导致重复属性 + 多余 `>`

- **场景**：给 示例预算表/实际.cpt 的 r3 表头格挂条件属性（参数为空→列宽 0）时，用字符串切片重建单元格标签。
- **报错原文**：损坏产物（示例预算表.cpt L2570）：`<C c="58" r="3" c="58" r="3" s="4">><O>`；验证输出 `示例预算表.cpt: XML ✗ ...`。
- **根因**：重建用了 `f'<C c="{col}" r="3"{pre[pre.find(" "):]}>'`，而捕获组 `pre` 本身已含完整属性串和闭合 `>`（形如 ` c="58" r="3" s="4">`），拼出「属性重复 + `>>`」双料损坏。
- **正确做法**：重建标签只保留需要的属性（先 `re.search(r' s="(\d+)"', ...)` 单独提取 s），或直接在原标签 `>` 前插入子元素而非整体重建；写盘后必须 `ET.parse` 立即验证，失败时按 `line (\d+)` 打印出错行原文。修复按「精确单点 → 去重 → 批量循环至无匹配」三级推进。
- **出处**：`_runs/tmp_add_cond2.py`（肇事）→ `_runs/tmp_dbg2570.py`（定位）→ `_runs/tmp_fix2570.py` / `tmp_fix_dup.py` / `tmp_fix_all_dup.py` / `tmp_fix_xml.py`（三级修复）。

### 2. RelatedFormula 条件公式参数名未包 `${}`（静默失效）

- **场景**：条件属性公式 `LEN('para_ext1') = 0`——XML 完全合法，fr_check 不报错，但列宽 0 的条件永不命中，"参数为空隐藏列"功能整体无效。
- **报错原文**：无任何报错（静默逻辑错误）；终态统计输出 `残留未包裹={err}`。
- **根因**：FR 公式里参数必须写成 `${para_ext1}`；裸参数名只是字符串字面量，`LEN('para_ext1')` 恒 ≠ 0。
- **正确做法**：注入模板统一 `LEN('${param}') = 0`；事后用 `re.findall(r"LEN\('(?!\$)", txt)` 扫描残留裸参数名作为终验步骤。
- **出处**：`_runs/tmp_fix_final.py`、`_runs/tmp_fix_xml.py`。
- **查重/参见（R31）**：同症状族见 ckzl/lc/08 §16.2 两行——『用 0mm 行高做条件属性隐藏可能静默失效』(doc-954：writeXML 丢弃字面量 0) 与『条件属性隐藏**列**不生效、隐藏**行**正常』(doc-1698：ColWidthHighlightAction 求值环境守卫不打日志)。症状同、根因异（本条=公式参数裸名恒假），同症状排查按三因逐一过。

### 3. JS 显隐列方案整体被 FR 原生条件属性替换

- **场景**：可选对比列（para_ext1~5 为空→隐藏列块）最初用 afterinit 注入 JS：`setTimeout` + `_g().getColumn(c).setWidth(...)` + 参数变更时 `location.reload()`。
- **报错原文**：无直接报错；方案缺陷为设计级——依赖渲染时机 500ms、reload 暴力刷新丢状态、`catch(e) {}` 把 API 失效全部吞掉。
- **根因**：用前端 JS 模拟 FR 引擎能力；FR10 本身支持条件属性 `<ColumnWidthColumn><width>0</width>` 由服务端完成显隐。
- **正确做法**：列显隐/列宽控制优先 FR 原生条件属性（FormulaCondition + ColumnWidthColumn Action），挂在表头格上；JS 仅做 FR 能力之外的交互。替换方案时必须先移除旧 JS Listener（按标记词「显隐联动 / toggleExtCols」正则删块），防止双方案叠加。
- **出处**：`_runs/tmp_add_toggle.py`（被推翻方案）→ `_runs/tmp_add_cond.py` / `tmp_add_cond2.py`（替换+清旧）。
- **查重/参见（R31）**：走 FR 原生条件属性路线前，先读 §16.2 doc-954 / doc-1698 两行已知坑（0 值被丢弃 / 列隐藏求值守卫），落地时对照规避。

### 4. 一次性脚本自身崩溃：group 越界 + 函数定义在使用之后

- **场景**：`tmp_add_cond.py` 挂条件属性首版，从未成功执行过一次。
- **报错原文**：正则 `r'<C c="(\d+)" r="3"[^>]*>((?:(?!</C>).)*)</C>'` 只有 2 个分组却调用 `m.group(3)`（IndexError）；`body_body()` 在主循环调用之后才 `def`（NameError）。
- **根因**：写完直接对生产 cpt 全量跑，没有先用单格小样自测。
- **正确做法**：一次性脚本也要「先 1 格 dry-run 再全量」；helper 函数定义放最前；正则分组数与 group 调用对齐。同族事故还有 `tmp_verify_pactqs.py`（见条目 7）。
- **出处**：`_runs/tmp_add_cond.py` → 由 `_runs/tmp_add_cond2.py` 重写救回。

## 二、SQL/CPT 内嵌 SQL 编辑族

### 5. SELECT 列表中间插行漏逗号

- **场景**：给 PACT年度汇总表 m_data 的 bpc_data CTE 增加 `obp_qs` 列，新行插在 `AS obp_internal` 行之后，忘了给上一行补逗号。
- **报错原文**：库上执行 SQL 语法错误（验证脚本输出 `!! 执行失败:`）；修复脚本 docstring 直书「补 obp_internal 后的逗号」。
- **根因**：文本行插入式改 SQL，插入点破坏了上一行的列表分隔符。
- **正确做法**：插入 SELECT 列表行的脚本，模板必须写成 `old + "," + "\n" + new_line`（把上一行逗号连同修改）；改完必跑「静态替换参数→库上执行」验证闭环（见条目 29）。
- **出处**：`_runs/tmp_pact_qs_fix.py`（肇事）→ `_runs/tmp_fix_comma.py`（修复）。

### 6. `re.sub(count=1)` 打中第一个同名片段，改错 CTE（静默数据错误）

- **场景**：把 join_final 的 `NULL AS obp_qs` 改为 `bpc.obp_qs`，但 `NULL AS obp_qs` 在 month_data CTE 里也有一份；`count=1` 按文本顺序命中了前者。
- **报错原文**：无报错——XML 合法、SQL 合法，但 obp_qs 列全 NULL（数据语义错）。修复脚本 docstring：「修正 obp_qs 替换位置错误: 还原 month_data, 正确改 join_final」。
- **根因**：同一别名片段在多个 CTE 重复出现时，"第一个匹配"≠"目标位置"。
- **正确做法**：替换前先定位锚点并断言相对位置（`i_bpc = t.find('bpc_data AS')`，`assert i_bad < i_bpc` 才是 month_data 内）；或用带上下文的多行正则；改错后按位置精确交换（先改后面的 join_final，再改前面的 month_data）。
- **出处**：`_runs/tmp_pact_qs_fix.py`（肇事）→ `tmp_diag_obpqs.py`（诊断）→ `tmp_swap_obpqs.py` / `tmp_fix_obpqs.py`（修复）。

### 7. 验证脚本复制修改变量名错位，出「稳健版」迭代

- **场景**：验证 PACT m_data 的首版脚本 `qs_i = block.index('<Query>')` 之后却用 `block[qs:]`。
- **报错原文**：NameError: name 'qs' is not defined（脚本崩在切片处）。
- **根因**：复制上一脚本改局部时变量改名不全。
- **正确做法**：验证脚本小改动后必须先空跑一遍再当模板复用；`_verify_pactqs2.py`（稳健版）同时补了 `${if...}` 条件宏剥离（`re.sub(r'\$\{if[^}]*\}', '', sql)`）与结果判读（"数据未到、通路正确即可"的降级结论）。
- **出处**：`_runs/tmp_verify_pactqs.py` → `_runs/tmp_verify_pactqs2.py`。

## 三、数据集与连接族

### 8. 整块替换 TableData 丢失 `<Connection>`（XML 合法但运行期取数失败）

- **场景**：用新 SQL 整体替换两 cpt 的 ds_fs 块，新块只有 Parameters+Query，丢了 `<Attributes maxMemRowCount="-1"/>` 和 `<Connection>`。
- **报错原文**：ET.parse 通过、无结构报错；预览时数据集无法取数。修复脚本 docstring：「修复 ds_fs 块: 补回 <Attributes maxMemRowCount> + <Connection>」。
- **根因**：DBTableData 的 Connection 声明是数据集取数的必要件；文本整块替换最容易截掉"尾巴"元素。
- **正确做法**：重建 TableData 块的模板必须含全 `class="com.fr.data.impl.DBTableData"` + Parameters + Query + Connection；替换前先摘取旧块的 Connection/Attributes 复用。凡整块替换，替换前后都 `ET.parse` + 块内 `NameDatabaseConnection` 存在性检查（幂等跳过）。
- **出处**：`_runs/tmp_replace_dsfs.py`（肇事）→ `_runs/tmp_fix_conn.py`（修复）。
- **查重/参见（R31）**：README『Index: 0, Size: 0』条目同族（TableData 结构残缺，症状层不同：彼为导入侧行列越界，本条为取数失败）；另参见 §16.2 doc-4153『模板能打开、预览无数据/报错——先查连接名/权限』，同一症状的环境层成因，本条根因在模板内连接声明缺失。

### 9. 数据集 Parameters 声明与 SQL 中 `${}` 不同步

- **场景**：ds_fs 的 SQL 引用 `${para_adj}`，但替换后的参数声明清单漏掉/残留 para_adj，级联与切换逻辑静默失效。
- **报错原文**：无直接报错；表现为参数切换无效。修复脚本操作记录：「示例实际表删 para_adj 参数」（SQL 已不用时反向残留同样有害）。
- **根因**：SQL 与参数清单分处同一块的两段，改一处忘另一处。
- **正确做法**：生成块时用同一份参数清单同时渲染 SQL 校验与 `<Parameter>` 列表；终验正则对拍「SQL 中 `${name}` 集合 == Parameters name 集合」。
- **出处**：`_runs/tmp_replace_dsfs.py`、`_runs/tmp_fix_conn.py`、`_runs/tmp_add_paraadj.py`。
- **查重/参见（R31）**：**同 README『级联参数静默失败』条目**（症状同族、根因互补：彼=Parameter 自闭合/SQL 未多行格式化，本条=声明清单与 `${}` 集合不同步；根因同源另见 填报报表开发错误分析.md §2/§3，不判重）。
- **警示（R31）**：终验对拍「SQL 中 `${name}` 集合 == Parameters name 集合」有两个防误报前提（R17 误报族教训）：①提取前先剥离 `${if...}` 宏体——宏体内列名/AND/IN 不是参数（族2 宏体标识符噪声）；②声明形态兼容 `<Parameter name=>` 与 `<Parameter><Attributes name=".."/>` 双形态及模板级 para_*（族5 声明形态盲区）——否则对拍会反向冤枉合规模板。

## 四、视图 / DDL / SQL 方言族

### 10. 视图定义中 `\$` 转义残留毁掉 FR 宏

- **场景**：entity_demob_ci 视图 DDL 里的 FR 条件宏被写成 `\$`，宏失效。
- **报错原文**：`pg_get_viewdef` 取回的定义含 `\$`；修复脚本断言 `assert "\\$" not in fixed, '仍有残留'`。
- **根因**：DDL 文本在写入链路中被反斜杠转义了一层。
- **正确做法**：从 `pg_get_viewdef` 取回定义 → `replace("\\$", "$")` → `CREATE OR REPLACE VIEW` 重建 → 再取 viewdef 断言无残留 → GRANT 补授权（重建视图会丢授权）→ 库上执行验证。
- **出处**：`_runs/tmp_ci_fix_dollar.py`。

### 11. f-string 生成 FR 宏 SQL 必须双写 `{{}}`

- **场景**：生成器把含 `${para_ver}` 的 SQL 写进 f-string。
- **报错原文**：单括号写法在 f-string 内会 KeyError/IndexError 或被当占位符替换成空。
- **根因**：Python f-string 的 `{}` 转义与 FR 宏 `${}` 语法冲突。
- **正确做法**：f-string 内一律 `'${{para_ver}}'`（v3 正确示范，见出处）；或整段 SQL 用非 f 普通字符串拼接（v2 的做法）。代码评审时 grep `f"""` 块内的单 `${`。
- **出处**：`_runs/tmp_gen_sus_v3.py`（正确）对照 `_runs/tmp_gen_sus.py`（拼接式）。

### 12. varchar 数据列直接 `::numeric`，空串炸转换

- **场景**：源表 hfm_fin_a/b 的 data 列是 varchar，存在空串 ''。
- **报错原文**：`invalid input syntax for type numeric`（直接 `data::numeric` 遇 '' 即炸）。
- **根因**：GaussDB/PG 中 `''::numeric` 非法（与 NULL 不同）。
- **正确做法**：统一 `COALESCE(NULLIF(data, '')::numeric, 0)`；同类还有 `nullif(trim(signeddata),'')` 再 cast。凡 varchar 数值列进表达式，先 NULLIF 后 cast。
- **出处**：`_runs/tmp_make_views.py`、`_runs/tmp_restore_budget.py`、`_runs/tmp_sus_probe2.py`。

### 13. `dec` 是关键字：月列/别名必须引号或改名

- **场景**：聚合 v_vave_project 的 12 月列 dec。
- **报错原文**：SQL 语法错误（dec 被解析为 DECIMAL 关键字）；探查脚本连续两版才稳定（「vave dec 加引号」→「dec 列别名校正」）。
- **根因**：列名 `dec` 需 `"dec"` 引用；别名 `AS dec` 同样非法。
- **正确做法**：`sum(coalesce(nullif("dec",'')::numeric,0)) AS dec_total`——列名加引号、别名改安全名。
- **出处**：`_runs/tmp_sus_probe2.py` → `_runs/tmp_sus_probe3.py`。

### 14. 跨表对账先核对维度取值格式（期间 'Apr' vs '9'）

- **场景**：用 fs_agg 反推实体口径时与 _vt 表对不上数。
- **报错原文**：无报错，数值不齐；脚本注释直书「fs_agg 用 'Apr' 英文月缩写, _vt 表用 '9' 数字?」。
- **根因**：同名维度列在不同域格式不同（月份英文缩写/数字、大小写 Actual/ACTUAL）。
- **正确做法**：对账第一步永远 `SELECT DISTINCT <维度> ... ORDER BY 1` 盘点两边取值域，再写 join/过滤；scenario 一律 `upper()` 归一。
- **出处**：`_runs/tmp_entity_scope2.py`、`_runs/tmp_scope_ppl2.py`。
- **查重/参见（R31）**：§16.2 doc-2597『directExportToExcel colNames 大小写不一致静默丢列』同属"名/键格式对齐"族（大小写/格式敏感的静默失配）；条目 16（前导零）为本族 SQL 侧同型，互为表里。

## 五、填报与表设计族

### 15. 填报表数据结构：宽表(m01~m12) 一天内被推翻回退长表

- **场景**：ADJ 调整表先改成 12 个月宽列（11:13），3 小时后改回 period/adj_data 长表（14:29），视图两次重建。
- **报错原文**：无报错；代价是 12 路 `CASE p.period::int WHEN 1 THEN a.m01 ...` 适配 + 视图重建 + 冒烟重跑。
- **根因**：FR 填报是"一行一格"提交，BuiltInSQLSubmiter 键=(年,实体,科目,期间) 天然对应长表；宽表是 Excel 思维的照搬。
- **正确做法**：填报输入表按长表设计（维度列+期间列+值列）；确需宽表展示交给报表层。
- **出处**：`_runs/tmp_adj_wide.py` → `_runs/tmp_adj_long.py`。

### 16. 期间前导零 join 不中（'03' vs '3'）

- **场景**：页面提交期间 '03'，视图侧 period 为 '3'，文本 join 静默不命中（ADJ 值没替换进去）。
- **报错原文**：无报错，页面汇总差为 0（期望非零）；加固脚本直书「期间 join 用 ::int(防 '03' vs '3')」。
- **根因**：varchar 期间列的文本等值比较对前导零敏感。
- **正确做法**：join 键两侧 `period::int` 归一；且写 Round D 类容错测试（故意插 '03' 验证仍命中）。
- **出处**：`_runs/tmp_adj_hardening_test.py`。
- **查重/参见（R31）**：与条目 14 同族（键/名格式对齐：'03' vs '3' 同 'Apr' vs '9'），互为表里；同类预防都是 join 键两侧归一（本条 `::int`）。

### 17. FR 提交是 INSERT 语义：同键重复行需视图层去重取最新

- **场景**：同一 (年,期间,实体,科目) 多次填报产生多行，页面汇总被叠加翻倍。
- **报错原文**：无报错，数值翻倍；加固脚本 Round B 专门验证「同键再填报→期望只认最新一条」。
- **根因**：IntelliDML/BuiltInSQLSubmiter 按配置可能是 insert 而非 update，表内天然存在同键多版本。
- **正确做法**：读侧视图用 `ROW_NUMBER() OVER (PARTITION BY 键 ORDER BY update_time DESC NULLS LAST, create_time DESC NULLS LAST)` 取 rn=1；只统计 `delete_flag=1`（软删除还原）；键列建索引。
- **出处**：`_runs/tmp_adj_hardening_test.py`、`_runs/tmp_make_adj.py`。

### 18. 库上冒烟测试必须事务回滚 + 测试标记

- **场景**：验证 ADJ 替换与 YTD 传导需要往生产输入表插测试行。
- **报错原文**：（若不回滚）测试数据污染页面真实口径。
- **根因**：验证性写入没有隔离手段。
- **正确做法**：`BEGIN → INSERT(带 create_by='test') → 查视图传导 → ROLLBACK → 复查 count 归零`；无法回滚的（autocommit 场景）用 `create_by='test'` 标记 + 结尾 DELETE 清理 + 残留断言「残留测试行=0, 页面汇总差=0.00」。
- **出处**：`_runs/tmp_verify_adj.py`、`_runs/tmp_adj_hardening_test.py`。

## 六、验证方法族（正面范式，直接复用）

### 19. YTD 累加不靠肉眼：程序化对拍累计关系

- **场景**：验证 CI 视图 YTD 列的正确性。
- **报错原文**：（eyeball 法的隐患）月度值合理不代表累计列正确。
- **根因**：YTD 是派生列，必须有独立的机器判定。
- **正确做法**：选行数最多的维度组（GROUP BY 全维度 ORDER BY count DESC LIMIT 1）→ 逐月 run_sum 对拍 ytd 列，`abs(diff)<1e-6` 逐行 ✓/✗，最后输出「全部通过/存在不一致」总判；维度含 NULL 用 `IS NOT DISTINCT FROM` 匹配。
- **出处**：`_runs/tmp_verify_ci_ytd.py`。

### 20. 权限子句用真实样本用户跑两态验证

- **场景**：挂完 entity 数据权限后验证管理员看全部、控制员只见授权实体。
- **报错原文**：（漏验后果）控制员越权可见或管理员看不到数。
- **根因**：只测"代码能跑"不测"两态数据面"。
- **正确做法**：从权限表取样——`SELECT user_gid FROM ...user_role WHERE role_id IN ('0','1') LIMIT 1` 取管理员、`...auth_base_user_map GROUP BY 1 ORDER BY 2 DESC LIMIT 1` 取授权最多的控制员；把样本代入 `${fine_username}` 各执行一遍并比对行数/实体集合；钻取页用控制员视角单独再跑。
- **出处**：`_runs/tmp_verify_perm.py`。

### 21. 视图缺科目三分排查法

- **场景**：汇整视图缺若干科目，需定位是源数据缺失还是过滤条件剔除。
- **报错原文**：无报错，页面行缺失。
- **根因**：视图=源数据∩过滤条件，缺行有两种成因混在一起。
- **正确做法**：①视图 `SELECT DISTINCT account` 求差集；②差集科目回源表**不带实体过滤**查行数（源无=上游问题，源有=权限/白名单过滤剔除）；③盘点 value/entity/custom3/view/period 各维度 DISTINCT 取值找口径错位。
- **出处**：`_runs/tmp_followup.py`。
- **查重/参见（R31）**：§16.2 doc-2365/576『无头预览/导出能打开、无异常，但一行数据都没有』(fr_task_* request 参数恒空 → Compare.IN 右值空恒假) 同属"无报错缺行"族——根因不同（本条=数据/过滤侧，彼=参数注入侧），排查时可并列对照。

### 22. 硬编码映射必须配 diff 巡检脚本

- **场景**：明细视图按硬编码 32 叶子 JOIN，科目树后续变化。
- **报错原文**：无报错，映射悄悄过期。
- **根因**：任何"写死清单"都会与活数据漂移。
- **正确做法**：固定一个 diff 脚本：当前边集解析叶子 vs 硬编码清单，输出「视图有-现在无 / 现在有-视图无 / 共有叶子的映射变化」三段；每次动树后跑一遍。
- **出处**：`_runs/tmp_diff_leaves.py`。

### 23. 科目树：叶子判定用反向闭包，最近祖先要多跳上爬

- **场景**：为明细科目挂汇整父科目（74 清单内）。
- **报错原文**：无报错；错误做法产物是映射 NULL 或挂错——脚本反例演示「64051105 直接父级不在74清单, 必须继续上爬」。
- **根因**：只看一层直接父级，遇到「直接父级也是中间汇总节点」就断链。
- **正确做法**：叶子判定=「不出现在任何 account_parent 中」（一次 NOT IN，反向闭包，等价于向下递归到空）；找父级=从叶子沿 parent_of 逐跳上爬直到命中清单（设 hop 上限 25 防环）；复核「叶子又当爹的应为空」。
- **出处**：`_runs/tmp_show_tree.py`、`_runs/tmp_diff_leaves.py`、`_runs/tmp_topdown_test.py`、`_runs/tmp_make_views.py`。

### 24. 切数据源先查维度完备性：合并口径丢 entity 导致权限失效

- **场景**：预算 _vt 表改源到 fact_detail（合并口径，entity 置 ''），随后整套方案作废回退 hfm_fin_b。
- **报错原文**：无报错；但 entity='' 使 entity 权限过滤恒假/全放行失效，钻取丢维度。
- **根因**：新源虽然省了拆分逻辑，却丢掉了权限与钻取依赖的实体维度。
- **正确做法**：换数据源前先列「下游消费的所有维度」（权限列/钻取参数/展示维度），逐列确认新源能供给；作废方案要有回滚脚本（本例 RESTORE INSERT+行数断言 325,720）。
- **出处**：`_runs/tmp_rebuild_budget.py` → `_runs/tmp_restore_budget.py`。

## 七、生成器与批量挂格族

### 25. 挂格脚本缺行守卫，静默覆盖 r3 表头标签

- **场景**：v3 全量挂载脚本对 `<C c="{col}" r="(\d+)"` 全行号替换，把 r3 表头的 LTA/PACT/示例模块/CI/CR/YTD/% 静态标签格也改成了数据绑定格。
- **报错原文**：无报错——XML 合法、绑定合法，仅表头显示错误；事后靠 r0-r3 扫描脚本发现，修复脚本 docstring：「恢复被 v3 误覆盖的 LTA/PACT/示例模块/CI/CR/YTD/% 标签」。
- **根因**：按列替换没有行号白名单。
- **正确做法**：所有按列批量改格的脚本加行守卫 `if row < 4: return m.group(0)`（表头/标题行只读）；修复后要**回写守卫到脚本本身**防重跑复发（本案例给 wire_cr/wire_budcr 补了 `row < 4`）。
- **出处**：`_runs/tmp_wire_all.py`（肇事）→ `_runs/tmp_scan_r03.py` / `tmp_scan_headers.py`（发现）→ `_runs/tmp_fix_hdr.py`（修复+加守卫）。

### 26. 批量挂格幂等三规则 + 无标识跳过

- **场景**：v3 全量挂载 40+ 列数据格，可能被重复执行。
- **报错原文**：（无幂等后果）重复注入/覆盖公式。
- **根因**：脚本重跑是常态不是意外。
- **正确做法**：①格子已有公式 → 保留不覆盖（`class="com.fr.base.Formula"` 探测）；②已有同款绑定 → 跳过（`dsName="..."` + 条件特征双查）；③行上找不到科目标识 → 跳过并计数；④结束汇报「新挂 N / 保留公式 N / 跳过 N」，可审计。
- **出处**：`_runs/tmp_wire_all.py`（正面示范）。

### 27. Excel 需求裁剪后的断链公式：换字面量 + 文本强制

- **场景**：按行区间裁剪示例项目需求 Excel 后，表头公式引用了已删除的辅助区行。
- **报错原文**：打开文件 #REF!/求值错误；脚本复核输出「残留断链公式: N」。
- **根因**：裁剪行不处理引用方。
- **正确做法**：先从原文件 `data_only=True` 读被引用格的缓存值，把断链公式整体替换为字面量；以 `=` 开头的描述文本强制 `cell.data_type='s'`（防 Excel 当公式）；收尾正则扫描所有引用行号 > 保留上限的残留断链归零。
- **出处**：`_runs/tmp_fix_headers.py`、`_runs/tmp_trim_req.py`。

### 28. 口径变更最小作用域：Var% 只改该改的行，其余留待定夺

- **场景**：示例实际表示例区 Var.% 的口径（值增幅 vs 百分点差）与 示例预算表权威口径不一致。
- **报错原文**：无报错，口径混用（比率减法当差值展示）。
- **根因**：复制示例区公式时未同步口径变更。
- **正确做法**：改口径脚本明确「仅改 35-36 行(有%值的行); 31-34 行保留原示例待用户定夺」——作用域白名单 + 未决项显式留痕；随后全扫 `IFERROR` 类旧公式残留归零确认。
- **出处**：`_runs/tmp_fix_varpct.py`、`_runs/tmp_clean_growth.py`。

## 八、通用脚本工程族

### 29. 「cpt 内 SQL → 库上验证」标准闭环五步

- **场景**：所有新写/新改数据集 SQL 的统一验证手法（示例项目反复使用的成熟范式）。
- **报错原文**：缺步骤的后果——未替换参数 `${...}` 直接发给数据库报语法错（`!! 未替换参数: [...]` / `!! 执行失败:`）。
- **根因**：FR 条件宏 `${if(len(para_year)=0,1950,para_year)}` 等不是数据库语法。
- **正确做法**：①定位 `<TableData name="X"` 块提取 `<Query>` CDATA；②静态替换：普通参数逐个 replace，`${if...}` 特例单独替换，`fine_username` 用真实样本；③**leftover 检查**：`re.findall(r'\$\{[^}]*\}', sql)` 非空即停；④执行并输出行数+各列非零行数+样例；⑤失败打印异常前 400 字符。
- **出处**：`_runs/tmp_verify_dsfs_sql.py`、`_runs/tmp_verify_perm.py`、`_runs/tmp_verify_cr.py`。
- **警示（R31）**：闭环工具自身可假绿——verify_sql.py 对不平衡 `${if(...)}` 实测会"未提供值→整段替换空串"并报『✅ 执行成功』（R36 证据，见 R17 REPORT ⑤.8）；闭环结论必须含**行数断言**而非"执行成功"字样，宏解析失败应 WARN 保留宏原文。

### 30. 74 科目 IN 清单在 ≥6 个脚本复制粘贴，无单一真源

- **场景**：74 科目常量清单出现在 make_views/replace_dsfs/restore_budget/diff_leaves/show_tree/followup 等脚本中各存一份。
- **报错原文**：无（尚未漂移，但属必然风险——diff_leaves 已证明树会变）。
- **根因**：一次性脚本各自内联常量。
- **正确做法**：常量落 `_runs/accounts74.json`（或仓内 csv），脚本统一加载；与条目 22 的 diff 巡检配套。
- **出处**：`_runs/tmp_make_views.py`、`_runs/tmp_replace_dsfs.py`、`_runs/tmp_restore_budget.py`、`_runs/tmp_diff_leaves.py` 等（改进发现，非已发生错误）。
